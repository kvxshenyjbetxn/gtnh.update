# GTNH Updater — специфікація

Статус: реалізацію розпочато. Є каркас, конфігурація, локалізація, теми та редактор правил. Додано каталог офіційних стабільних і beta/RC релізів. Підтримку нічних збірок вилучено за рішенням користувача. Завантаження архівів наразі відкривається у браузері; автоматична міграція ще не реалізована.

## Мета

Окрема десктопна програма для безпечної підготовки нової версії GT New Horizons із перенесенням вибраних користувацьких файлів. Позбавляє необхідності щоразу вручну збирати налаштування, карти та інші дані після оновлення.

## Платформи та розповсюдження

- Обов'язкова підтримка macOS, Linux і Windows від початку розробки; поточна розробка — на macOS. Див. `AGENTS.md`.
- Портативне розповсюдження без обов'язкового встановлення. Налаштування зберігаються окремо, у користувацькій папці ОС, не поруч із виконуваним файлом.
- Автоматичного оновлення самої програми немає.
- Для macOS погоджено підпис програми. Наявність Apple Developer membership і сертифікатів ще потрібно перевірити; підпис Developer ID та нотаризація — окремі кроки розповсюдження, незалежні від мови програмування.
- Конкретні формати портативних пакетів і мінімальні версії ОС уточнюються перед налаштуванням збірок. Потрібно врахувати WebView2 на Windows, системні залежності Linux та архітектури процесорів.

## Стек

- Rust — незалежне від інтерфейсу ядро оновлення.
- Tauri 2 — десктопна оболонка.
- TypeScript, Svelte, Vite — інтерфейс.
- `reqwest` — HTTP, `tokio` — асинхронні операції.
- `serde` та JSON — конфігурація й правила перенесення.

Ядро відповідає за каталог релізів, завантаження, розпакування, планування перенесення й створення результату. Tauri надає команди інтерфейсу та передає прогрес і помилки. Ядро має тестуватися без запуску GUI; консольний інтерфейс наразі не входить до обсягу робіт.

Rust-ядро розміщене безпосередньо в кореневій `src/` (`lib.rs`, `releases.rs`, `selection.rs`), поруч із файлами інтерфейсу. Кореневий `Cargo.toml` описує пакет `gtnh-core` і workspace із Tauri-оболонкою `src-tauri/`. Окремої папки `crates/gtnh-core` немає.

## Режими роботи

### Клієнт

1. Користувач обирає старий інстанс і папку інстансів Prism Launcher.
2. Обирає цільову версію GTNH та відповідний варіант Java.
3. Переглядає стандартні правила перенесення та додає власні.
4. Переглядає план копіювання і замін.
5. Програма завантажує офіційну збірку та створює окремий готовий інстанс у Prism із вибраними даними.

Не обмежуватися ZIP для ручного імпорту. Старий інстанс не змінюється. Обліковими записами Minecraft керує Prism, а не ця програма.

Структуру офіційних ZIP, метадані інстансу та спосіб його появи в Prism потрібно перевірити перед реалізацією. Створення інстансу не є підтвердженням успішного запуску Minecraft; наявність сумісної Java перевіряється окремо.

### Сервер

1. Користувач на ПК обирає локальну папку старого сервера та місце для нової.
2. Обирає версію GTNH і варіант Java серверної збірки.
3. Налаштовує перенесення та підтверджує план.
4. Програма готує окрему нову серверну папку.
5. Користувач вручну переносить результат на сервер.

Програма не підключається через SSH/SFTP, не встановлюється обов'язково на сервері та не керує віддаленим процесом Minecraft. Перед копіюванням активного світу сервер має бути зупинений. Вибір Java серверної збірки стосується цільового сервера, а не лише ПК, на якому готується папка.

Каталог містить окремі MultiMC/Prism і Server ZIP, варіанти Java та позначки stable/beta. Потрібно використовувати фактичні посилання, а не конструювати URL за фіксованим шаблоном: назви й діапазони Java змінюються.

## Перевірка нових версій GTNH

- Автоматична та ручна перевірка нових версій збірки.
- Глобальний збережений перемикач «Показувати тестові версії», спільний для клієнта й сервера.
- За замовчуванням вимкнений: лише стабільні релізи.
- Увімкнений: стабільні та beta/RC, включно з фінальним релізом після RC.
- Одне налаштування керує списком версій і обома способами перевірки оновлень.
- Нічні збірки не підтримуються: немає каталогу, перемикача або запитів GitHub Releases API. Застарілий ключ `includeNightlies` зі старих конфігів ігнорується при читанні та не записується знову.
- Після вимкнення beta не пропонувати старішу стабільну версію як оновлення.
- Порівнювати версії з урахуванням prerelease, не лексикографічно й не лише за порядком на сторінці. Спеціальні випуски, наприклад першоквітневі, не повинні випадково ставати рекомендованим оновленням.
- Перевірка не означає автоматичного встановлення або синхронного оновлення клієнта й сервера. Для гри їхні версії GTNH мають збігатися.

Частота фонової перевірки та поведінка при закритому вікні ще не погоджені.

## Правила перенесення

- Окремі збережені списки для клієнта та сервера.
- Кожен містить стандартні правила за вікі та власні доповнення користувача.
- Можна додавати файли й папки та вимикати непотрібні правила.
- Додавання через системні діалоги вибору файлів/папок, без ручного введення шляху. Спочатку користувач вибирає поточну збірку. Для клієнта можна вибрати інстанс Prism із вкладеною `.minecraft` або саму ігрову папку.
- Вибір обмежений вмістом поточної збірки; після канонізації шлях має залишатися всередині джерела. Зберігати відносний шлях із `/`. Джерела клієнта й сервера зберігаються окремо.
- Правила повторно використовуються під час наступних оновлень.

### Стандартні клієнтські дані

Шляхи відносні до `.minecraft` старого інстансу:

- `config/vendingmachine/favourites`
- `config/shaders.properties`
- `ESM`
- `journeymap`
- `resourcepacks`
- `saves`
- `schematics`
- `screenshots`
- `shaderpacks`
- `TCNodeTracker`
- `visualprospecting`
- `BotaniaVars.dat`
- `localconfig.cfg`
- `options.txt`
- `optionsnf.txt`
- `servers.dat`

`backups` — опційно: вікі зазначає, що вони не потрібні, якщо старий інстанс збережено. Відсутні необов'язкові файли не повинні блокувати міграцію.

Не переносити весь `config` або `mods` за замовчуванням. Додаткові моди, `serverutilities` і власні зміни конфігів потребують окремого усвідомленого вибору та попередження про сумісність.

### Серверні дані

Серверна вікі описує оновлення на місці; підготовка нової папки — адаптація цієї інструкції.

- Брати нові `config`, `libraries`, `mods`, а також `resources` і `scripts`, якщо вони присутні, із нового релізу.
- Для Java 17+ брати актуальні файли запуску й допоміжні файли з нового архіву, а не старі копії.
- Зберігати `config/JourneyMapServer`: там UUID, потрібний для прив'язки клієнтських карт.
- Не накладати старий `config` цілком; індивідуальні зміни переносити вибірково.
- Повний список стандартних серверних даних ще потрібно перевірити на реальній структурі збірки, включно з назвою папки світу та адміністративними файлами. Не припускати, що світ завжди називається `world`.

### Конфлікти

- Стандартні правила вікі: переносити старі файли із заміною відповідних нових.
- Власні правила: за замовчуванням запитувати; дозволити зберегти вибір «Замінювати», «Залишати новий» або «Запитувати».
- Перед виконанням показувати заплановані заміни.
- Копіювання папки не повинно означати непомітне видалення всіх нових файлів із неї: точну семантику об'єднання й конфліктів потрібно визначити в плані реалізації.
- Старі клієнтські та серверні папки ніколи не змінювати.

## Конфігурація програми

Використовувати стандартний шлях Tauri `app_config_dir`, а не жорстко заданий домашній каталог:

| ОС | Типовий шлях |
| --- | --- |
| macOS | `~/Library/Application Support/<app-id>/` |
| Windows | `%APPDATA%\<app-id>\` |
| Linux | `$XDG_CONFIG_HOME/<app-id>/`, або `~/.config/<app-id>/` |

- Створювати папку за потреби.
- Зберігати глобальний канал релізів, мову, тему та окремі правила клієнта й сервера.
- У налаштуваннях — кнопка «Відкрити папку конфігурації», що відкриває фактичну папку в системному файловому менеджері.
- Безпечне збереження через тимчасовий файл із заміною; при помилці не втрачати попередній конфіг і показувати зрозуміле повідомлення.
- Не обіцяти гарантованого запису за будь-яких умов: можливі брак місця й відмова доступу. Пошкоджений конфіг не перезаписувати мовчки.

Для першого етапу використано ідентифікатор `app.gtnh.updater`, початкову мову — українську, тему — AMOLED. Це початкові технічні значення, які можна скоригувати до першого релізу; зміна app-id змінює шлях конфігурації.

## Інтерфейс

- Стриманий утилітарний інтерфейс: без рекламних гасел, демо-позначок, напису `Prism / Server` та згадок стеку в навігації. Не показувати недоступні операції як робочі.
- Дві теми: чорна AMOLED і світла.
- Дві мови: українська й англійська.
- Мова й тема зберігаються між запусками.
- Режими «Клієнт» і «Сервер», вибір джерела та призначення, каталог версій, редактор правил, попередній перегляд операцій, прогрес і результат.
- Помилки повинні пояснювати проблему та доступну подальшу дію.

## Безпека та обмеження міграції

- Не виконувати оновлення поверх старої збірки.
- Рекомендований механізм: готувати результат у тимчасовому каталозі й публікувати як готовий лише після завершення; невдалий результат не видавати за успішний.
- Перед копіюванням перевіряти шляхи, доступність джерела й призначення, вкладеність папок і наявність місця настільки, наскільки це можливо.
- Безпечно розпаковувати архіви: не дозволяти вихід за каталог призначення; політику символічних посилань визначити перед реалізацією.
- Вікі рекомендує спочатку перевірити запуск чистої збірки. У першій версії не обіцяти автоматичну перевірку запуску Minecraft.
- Вікі рекомендує оновлюватися послідовно між гілками: наприклад, 2.6 → 2.7 із завантаженням світів → 2.8. Саме копіювання через проміжні версії не замінює завантаження світу.
- Попереджати про ризик пропуску гілок і необхідність резервної копії світу. Після конвертації світу не гарантувати його сумісність зі старою версією.

## Перевірки

- Юніт-тести Rust-ядра: розбір каталогу, stable/beta/RC і спеціальні випуски, порівняння версій, правила перенесення та конфлікти.
- Файлові інтеграційні тести: відсутні файли, помилки запису, безпека шляхів, незмінність джерела, незавершені операції.
- Перевірка збереження конфігу, глобального каналу та розділення правил клієнта/сервера.
- Перевірка обох мов і тем, відкриття папки конфігурації.
- Збірки та платформні перевірки на macOS, Linux і Windows. Чітко розрізняти заплановану й фактично перевірену підтримку.
- Перевірка створеного інстансу в Prism та підготовленої серверної папки на реальних офіційних архівах.

## Відкриті рішення

- Назва, app-id, мінімальні версії ОС та підтримувані архітектури.
- Формати релізних пакетів, залежності WebView і доступність Apple-сертифікатів.
- Початкова мова й тема.
- Частота автоматичної перевірки GTNH і поведінка при закритому вікні.
- Визначення поточної версії, якщо метадані старої збірки відсутні.
- Точні серверні правила, семантика об'єднання папок і політика символічних посилань.
- Чи потрібна підготовка сервера без локальної копії світу; як пояснювати подальше ручне перенесення.
- Чи перевіряти запуск чистого інстансу окремим кроком користувача перед перенесенням.

## Поза поточним обсягом

- Автооновлення самої програми.
- SSH/SFTP, віддалене керування сервером і його автоматичний перезапуск.
- Консольний режим.
- Автоматичне об'єднання довільних конфігів і гарантія сумісності додаткових модів.
- Автоматична конвертація світів між гілками без запуску Minecraft.
